# Data sources and their quirks

- **playwright-scraper turns playwright-stealth on by default**, and its injected scripts throw inside some pages' own JS (schoolz's own SPA renders an empty shell) or blow the render's memory budget (Beck's Finalsite directory: 900MB+ with it, 8s without), which schoolz counts as the scraper being unavailable. The primary ran without it for months before it became playwright-scraper, so `scraper_client._with_stealth` keeps it off there unless a caller passes `stealth=True`; the droplet and Pi keep their default. It also cut Finalsite rosters short (Kresson: 9 of 24).
- **A source that 403s Fly's addresses** (Chesterbrook's Cloudflare, Wood-Ridge's Fastly: 200 from a home network with the same request) goes through `scraper_client.get_bytes` (a file: plain GET, then the scrapers' raw fetch) or `fetch_html_from_any` (a page behind a bot challenge, which a raw fetch only gets the challenge for; each scraper is asked until one returns the page the caller recognises).
- **Smore** — client-rendered Svelte, no API/RSS; scraper with `wait_for_selector=".block-wrapper"` (present on every block type).
- **Lunch menus** — one PDF per (grade band, meal type) per month; discovery anchors on the `-MS-Breakfast`-style suffix to tolerate real filename typos; parsed as a native `document` block; deduped on PDF URL. A bare month+year PDF counts as the type of a single-type district. `LunchMenu` also supports school-scoped rows. **SchoolCafé** (`District.schoolcafe_shortname`, `services/schoolcafe.py`) is a public JSON API, no model; only unambiguous school-name matches count. It 503s in bursts (Barrington at 3:00 ET failed nightly for a week while neighbours at 3:04+ didn't), so `_get` retries twice; its errors classify as `source_unavailable`, never `scraper_unavailable`, since no scraper is involved. **FD MealPlanner** (`School.fdmealplanner_location` = `tenant/account/location`): the per-day `/meals` endpoint answers a bare request (only the one-time org search needs the client-encrypted token); items on ≥60% of the window's days are standing options and dropped so the rotating entrée shows; the endpoint clamps to its `monthId`, so one call per month.
- **Google Sites menu pages** (Burlington Township, `School.presence_menu_page_url` = a `sites.google.com/...` page, `services.lunch_menu.list_google_sites_menu_files`) — the page embeds the month's menus as Drive files titled by hand ("October 2026 young school lunch.jpg"); each Drive title is read from the file's `/view` page and fed to the same `pick_presence_menus` as a Presence site. One page per school keeps schools that share a type but not a menu apart. The model sometimes files a price box from the blank cells of a partial first week under a real date, so `parse_menu_pdf` drops any entry matching "meal prices"; rewording the extraction prompt to prevent it made the model skip real days, so don't.
- **Aramark MySchoolPlate** (`School.myschoolplate_location` = `tenant/location-key`, `services/myschoolplate.py`) — a Next.js app over a GraphQL mesh; the mesh URL and store code are in the page's own config, so a tenant needs no setup. Public GET with a fixed API key; the catalog call fails without the Magento store headers (the meal-period and category lookups don't need them). Entrées are products on stations *named* "Entree"/"Daily Serve Entree"/"Express"/"Grill" (station ids resolve via `Commerce_categoryList`), minus sides by `master_recipe_type`; a product's own type alone mislabels items (a bean side is "Breakfast Meat"). `MONTHLY` returns whole weeks, so filter to your window. Same standing-items rule as FD MealPlanner/Health-e Pro. **A location can have no API menu at all** (Willingboro's elementary and early-childhood schools): its page then lists the month's PDFs as client-rendered links ("Elementary Lunch"), month printed inside the PDF and the asset URL replaced in place, so `lunch_menu._discover_myschoolplate_menus` (district `food_services_menu_url` = `https://<tenant>.myschoolplate.com/en/locations`) classifies by link text, reads the month off the PDF and appends it to the URL as a fragment so each month is a new key. A null month answers `locationRecipesMap: null`, not an empty list.
- **Nutrislice** (`School.nutrislice_location` = `district/school-slug`, `services/nutrislice.py`) — a public JSON API, no key; one call per Sunday-to-Saturday week. Entrées are the foods filed `food_category: "entree"`; an elementary breakfast often has none (a muffin is a "grain"), so a breakfast day without one falls back to its grains. Same standing-items rule as the other vendors.
- **Staff directory as a document** (`School.staff_directory_url`, `staff_roster.fetch_directory_document`) — a PDF table, `.xlsx` (read with zipfile, no spreadsheet dependency), Google Slides deck (public `/export/txt`) or a published Google Sheet (the `/d/e/<key>/pubhtml` iframe a page embeds; read through its CSV export, "First Name"/"Last Name" columns joined). Columns are found by header text, the header carries across pages (sheets print it once), and "Last, First" is flipped. Fetched through the scraper's `/fetch-raw` because a bot-walled site 403s plain GETs. Rows carry no as-of date, so a stale sheet looks current.
- **Staff rosters** — Finalsite `?const_page=N` pagination *looks* server-side but is client-side (page 2 returns page 1), hence `/fetch-paginated` clicking `.fsNextPageLink` in one session. `StaffMember.title` is `None`, never `""`. `staff_roles.classify_role` (narrow, for the "Who to contact" grid) vs `classify_directory_category` (coarser, for directory filters, derived at query time so keyword tuning needs no migration/backfill).
- **School documents** — discovery tries site nav, then already-parsed Smore blocks (some handbooks exist only as a Google Doc link in a newsletter). Lookups are scoped to `<main id="fsPageContent">`, or a footer Drive link gets attributed everywhere. Max `academic_year` wins; nav and newsletter genuinely disagree.
- **School info** — Finalsite footer widget. Pages have **two** `<footer>`s (first hidden), so wait on `.fsLocationAddress`. Logo is the first `<header>` `<img>`, skipping a Google Translate badge.
- **District calendars** — on older Finalsite sites the `.ics` URL is never in the page; the subscribe button hands it to `navigator.clipboard.writeText()` (found by intercepting that write): `https://{domain}/fs/calendar-manager/events.ics?feed_id={uuid}`. `District.ics_feeds` carry `school_types`. Dedup runs both ways: the feed *claims* a matching newsletter row; `external_uid` makes re-scans idempotent.
- **Marking periods / transportation / preschools** — deterministic BeautifulSoup, no LLM, so dates can't be mis-zipped to columns. Real gremlins (NBSP in headings, weekday-prefixed dates, footnotes glued to dates) have fixtures in `tests/fixtures/`.
- **HS day rotation** — pdfplumber word coordinates; entries snap to the *nearest* month header (at-or-left mis-assigned months), headers sharing a line with entries are peeled off first. The sheet is "tentative", so vanished rows are deleted.
- **DigitalSports** (`<school>.digitalsports.com`, `services/digitalsports.py`, same `athletics_calendar.scan` job as ArbiterLive, `source="digitalsports"`) — plain httpx, no auth. The schedule page pages by week through `/pages/schedule/call-school-ajax.php?filter=bydate&date=YYYY-MM-DD` (that date plus six days, HTML); the scan steps from a Monday over the window. Not the FullCalendar feed (`schedule-json.php`, POST with Unix `start`/`end`): it keeps the originals of rescheduled games and omits some the page lists. Away games have no `.opponent` span; the venue is the link whose `onclick` opens `details.php` (the opponent can be a tooltip link too). Practices are dropped; a team-less "School Event" row is named from the details text. Rescheduled/removed games vanish from the pages, so the scan deletes the school's rows in the window that are no longer listed (Arbiter's never does). `SchoolContentItem.source` is 20 characters, hence `digitalsports`, not `digitalsports_athletics`. No cancelled-game markup has been seen on the site.
- **School events doc** (`services/school_events_doc.py`) — a year-at-a-glance Google Doc, regex-parsed. Three columns interleave in the txt export, so only each line's own date counts. Closures/breaks skipped (district feed owns them), month-only lines skipped, vanished lines deleted, an empty parse never prunes. Not a class-page source.
- **Google Sites** — server-rendered, plain httpx. Text extraction recurses only into *inline* descendants and lets each nested block be visited on its own; skipping any block with a nested block descendant discarded real loose text. "Button" widgets have no `href` server-side (resolved by a `jsaction` handler) — a known gap.
- **Weather** (`services/weather.py`) — NWS hourly over the school-day window (adjusted for early dismissal / delayed opening) + EPA UV by ZIP; keyless, deterministic what-to-wear rules. `School.latitude/longitude/nws_grid` filled by `school_info.scan` (reset on address change): Census geocoder, then Nominatim. Cached per gridpoint for an hour with a short timeout. No hours on file → "morning/afternoon", never a guessed bell time. After the window closes, and on weekends/closed days, shows the next school day (`pick_weather_day`).
- **Due-date years** (`bucket3_extract.resolve_due_date`) — Classroom prints the year exactly when month/day would be ambiguous; an explicit year must win over the Jul–Jun inference, or last year's work reappears as current (and, via `late_credit`, can hide live work). `kids_view.MAX_PLAUSIBLE_DAYS_LATE` guards bare dates.
- **Chesterbrook's own files** (`special_events.scan`, `services/special_events.py`) — its Calendars & Menu page lists each month's special-events calendar *and* lunch menu PDF, both read by one scan; menus are stored as the school's own `LunchMenu` with portion sizes stripped. The page ignores `?mm=` (every month's URL serves the same list), so a PDF's month comes from its filename; and it lags the uploads (October's menu sat under `wp-content/uploads/.../2026/10/` while the page still listed September), so a missing month is probed at its predictable WordPress upload path.
- **Incident IQ public calendars** (`services/incidentiq.py`) — a district's facilities-booking calendars, embedded as a widget that loads after the page. An anonymous POST of the widget's `ViewId` returns the events; a feed is stored in `District.ics_feeds` as `https://<tenant>.incidentiq.com/api/event/events?ViewId=<guid>` (a key, not a GET endpoint) and `fetch_district_calendar` routes it. Events have no id, so the uid hashes title + start + rooms. Never wire a district-wide view beside the per-school ones: it is their union, and district-feed uids are subtracted from school feeds.
- **Staff directory discovery** — when no known path yields a roster, `staff_roster.find_directory_links` follows the school's own "Staff Directory" nav link, same host only (a subsite's link to the district directory would list every school's staff). A directory that lists a whole district on one page with each person's school on their own profile (Berlin Township) puts `locations` on each item, and `drop_sibling_school_staff` splits on that before falling back to titles.
- **A subsite directory that redirects to the district's** (Lenape Regional: each school's `/our-school/staff-directory` lands on the district site's full list) — a known path or same-host link can still end up there. `_read_constituent_directory` re-reads it filtered to the school's own Location option (Finalsite `const_search_location=<id>`), on the final URL, because the redirect drops a query string. Only a filtered read that got every card the pagination label promises tags `location_filter`, which lets the scan delete numeric-id rows it no longer lists. Every other read only adds and updates, never removes.
- **SACC** is deliberately not a recurring job — a one-off script; re-run by hand if the handbook changes. Only `site_phone` is per-school.

## Newsletters

**Newsletters.** `smore.scan` is the preferred path (public URLs, scraper only). `email.scan` needs a connected Gmail (read-only) and exists to *discover* newsletter links; `EmailScanner.school_id`, when set, auto-creates the discovered link's scan job (`smore.scan` or `mailchimp.scan`).
- **An email scan keeps links, never mail** (`services/email_links.py`). Only page URLs of the kinds the scanner ticks (`EmailScanner.link_kinds`, catalog in code) survive, reduced to their public form with the query dropped (a "view in browser" link carries `?e=<subscriber id>`). Click-tracking redirects (`list-manage.com/track/click`, `out.smore.com`) and `eepurl.com` never match: their target is unknown without following them, and following one reports a click. Body, subject, sender and Gmail's snippet are read in memory and dropped; a processor error stores the exception type only. Migration 0118 blanked what earlier scans had stored.
- **An email-made issue scan stops itself.** The job the email scanner creates carries `params.stop_after` (email arrival + 28 days for Smore, + 14 for Mailchimp, whose sent campaigns never change); past it `issue_scan_over` turns the job off without fetching. An email bringing a known link again moves the date and re-enables the job, so a school reusing one Smore URL weekly stays scanned. Hand-made and archive jobs have no date and an email never adds one.
- **Mailchimp** (`source_type="mailchimp"`, `services/mailchimp_parser.py`) — server-rendered, plain httpx. Blocks are `.mceText`/`img.mceImage`/`a.mceButtonLink` (classic templates: `.mcnTextContent`/`img.mcnImage`/`a.mcnButton`); social icons have neither image class. The archive toolbar (`#awesomewrap`) and the unsubscribe footer are dropped. A campaign Mailchimp took down redirects to `mailchimp.com/about/mcsv-static` → zero blocks → `WARNING[mailchimp_no_blocks]`. Each issue is its own URL, like most Smore schools.
- **A new URL per issue is the common case.** Most tracked schools publish each issue at a fresh Smore URL, often weekly, and the job only re-checks the URL it's given — so each needs its URL swapped by hand per issue or a Gmail scanner to catch it. `smore.com/u/<username>` is an author profile, not a newsletter; issues live at `/n/<code>`.
- **An expired Smore link goes silent, not failed** — it renders a page with no `.block-wrapper`, indistinguishable from "nothing new". Zero blocks *fetched* is therefore `WARNING[smore_no_blocks]`.
