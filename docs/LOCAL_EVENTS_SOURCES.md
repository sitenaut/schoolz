# Local events sources

Per-source notes for `backend/local_events/` (the `/local` page). The pipeline-level rules live in `CLAUDE.md` → "Local events"; read that first. This file is the detail you need when touching one specific source.

## Scraping infrastructure

- **The shared Playwright droplet** (`LOCAL_EVENTS_SCRAPER_URL`/`_KEY`; key = billz's `RECIPE_SCRAPER_KEY`) is tried first, schoolz's own Fly scraper second. The droplet service is its own repo, **playwright-scraper** (alerts in Grafana's `scraper` folder). Its `/health` is liveness only; `/health/deep` says whether it can actually render. It supports stealth + extra waits and keeps these ~40-render runs off the 1GB Fly Chromium that already absorbs the scan bursts. A full run takes ~10 min.
- **Deploys are pulled, not pushed.** Two self-hosted GitHub Actions runners poll outbound (no inbound SSH, no deploy key in GitHub). A push to that repo's `main` touching `app/**`, `Dockerfile`, `requirements.txt`, `docker-compose.yml`, `deploy/**`, `tests/**`, or the workflows runs `checks.yml` (unit tests + a real-Chromium smoke test of the actual image) on GitHub's runners, then fans out only if it passes: `scraper-droplet` deploys the DigitalOcean droplet, `scraper-residential` deploys the residential Pi (`scraper.profitnaut.com`). Each fetches `main` and runs that commit's own `deploy/deploy.sh` (health gate + rollback). A weekly cron (Mon 14:00 UTC) redeploys with `--pull` for base-image patches. Grafana dashboards/alerts sync on a push touching `grafana/**` (`grafana/sync.py`). None of this touches schoolz's own Fly scraper, which ships with a manual `fly deploy` from `scraper/` (it isn't in `deploy.yml`).
- **The residential scraper is opt-in per call** (`fetch_rendered_html(prefer_residential=True)`), so the Pi doesn't absorb other sources' load.
- **Raw fetches run without playwright-stealth** (`fetch_raw_via_scraper`, behind every `ical_sources`/`rss_sources` entry with `via_scraper`): these feeds are public and robots.txt allows them, so the least evasive fetch that works is the one to make. Each came back without it: the library feeds from the droplet, the CivicPlus towns and Fieldsboro from a home address. No stealth gets the datacenter scrapers past a Cloudflare challenge anyway. A playwright-scraper too old to take `stealth` on `/fetch-raw` ignores the field and runs stealth. Rendered pages (`fetch_rendered_html`) keep their own `stealth` argument, on by default.
- **Or the scrapers' plain HTTP client** (`fetch_raw_via_scraper(via="request")`, a `tribe_sources` entry's `"via_scraper": "request"`): no Chromium, for a host that needs no JavaScript but refuses some addresses, or that no Chromium can load. It sends playwright-scraper's own User-Agent, `playwright-scraper/1.0`, never a browser's, so a site that turns away everything but browsers still gets to. A playwright-scraper older than that sends a Chrome one, so every scraper an entry can reach has to run it first, Fly's included (`scraper/SOURCE_REF`). An `accept` check stands in for the bot-challenge one: an answer it rejects goes to the next scraper.

## Distance (`/local`'s "within N miles of ...")

- **Where an event is** comes from `local_events/locate.py`, run at the end of every refresh. Few feeds publish coordinates, so it geocodes, in order: the event's `venue_address`; its `venue_name` (searched only inside a box around the region); the source's **`location`** param; and last, the spot most of that source's other events share. Answers, misses included, are cached in `geocoded_places`; a miss is retried after 30 days.
- **A feed that never states a venue needs `"location": "Town, NJ"` on its source entry** (any source type; town level is enough). Without it its events have no position. Set it when adding such a feed - check the run summary's `locations.unplaced`.
- **Unplaced events show at every radius.** The API keeps `latitude IS NULL` rows inside any radius on purpose: unknown is not "far away". The cost is that a far-away feed with no addresses and no `location` leaks into everyone's list.
- **Lookups are capped per run** (`MAX_LOOKUPS`) and Nominatim is throttled to one request a second per process, so a big new feed is placed over a few runs (`locations.waiting` in the summary), not one.
- **A refresh rewrites every field of an existing event**, so the upsert keeps the stored position when the feed gives none and the venue text is unchanged. Take that out and every run blanks the coordinates and re-places them from the cache.
- **Venue-name matches can be wrong** (the same name elsewhere in the box). The fix is the source's `venue_address`, or a `location`, not a wider search.
- **The visitor's side is browser-only** (`frontend/src/lib/eventsNear.ts`): the chosen point lives in `localStorage`, rounded to two decimals (about half a mile) before it is stored or sent, and a typed address goes to `POST /local-events/place` in the body so it never sits in a logged URL. Nothing about a visitor's location is stored server-side; `/privacy` says so - keep it true. The default (Cherry Hill, 15 miles) is a frontend constant; the API applies no radius unless asked, so the chatbot and other callers are unaffected.
- **Postgres `LEAST` skips NULLs**: the distance expression needs its `CASE` or an unplaced event comes out 12,437 miles away instead of NULL.

## Sources

- **Mt Laurel Y** (`deyra_schedule.py`) — the schedule renders inside `<deyra-finder>`'s shadow root. `wait_for_selector` pierces shadow roots but `page.content()` never includes them, so schoolz's scraper returned an empty shell and the Y silently became 0 events whenever the droplet was down (its render endpoint once 502'd for days while `/health` said ok — hence `/health/deep`). Fixed with `include_shadow_dom` on `/fetch-html` (inlined as `<template shadowrootmode="open">`). BeautifulSoup keeps `<template>` text as `TemplateString`, which `get_text()` skips, so the parser strips the template tags first. A source where every day fails raises; pages with no classes are a WARNING, not "0, success". Runs as its own job (`0 5,17 * * *`): 3 schedules × 14 days at ~1 min per page on prod's 1GB machine held every faster feed behind it.
- **Macaroni KID → Yodel** (`yodel_sources`, `sources/yodel.py`) — its `/events` page is an iframe of an `events.yodel.today` widget and its sitemap lists no events, so billz's `sitemap_sources` entry silently returns 0. The widget server-renders page 1 into the Next.js RSC payload; later pages come from the page's `fetchEvents` server action (POST with `Next-Action`), whose id changes on every Yodel deploy and is re-read each run. Yodel's Cloudflare blocks the widget for anything but a real browser on a residential IP (403 from Fly, from the droplet's stealth Chromium, and from plain curl on a home line), so on a 403 page 1 comes through the residential Pi. That's ~2 weeks of events, deliberately: paging means ~10 widget loads per run, and one such burst got the Pi's IP blocked. Don't turn paging back on without spacing loads out. Per-event pages 403 too, so links use the event's own website/tickets URL.
- **DPCalendar feeds need a date range** or return `{"events": []}` (confirmed on evesham-nj.org, which billz's default has therefore always fetched as 0). `JsonApiSource.request_url` adds today→+90d unless the URL sets `date-start`.
- **WordPress "The Events Calendar"** (`tribe_sources`, `sources/tribe.py`) — public REST API, so any site running the plugin is a params entry, no code. `start_date` is read as Eastern and the `*_utc` fields ignored: some sites' WordPress is set to UTC while editors type local times. visitsouthjersey.com is regional (thousands of events a year out, down to Cape May), hence `days_ahead` + `max_miles`; many venues have no coordinates, so a zip prefix stands in (080/081/190/191 near, 082–084 shore). Unmapped site categories are dropped, not slugified, so one site's taxonomy doesn't flood the category menu.
- **Camden County Library System** (`ccls_sources`, `sources/ccls.py`) — Drupal "Intercept" JSON:API, no scraper: `GET /jsonapi/node/event` filtered by `field_location.id`. Branch names in params are matched case-insensitively against a live `GET /jsonapi/node/location`, so branch changes need no code. The pseudo-locations ("Virtual", "Off Site", "System Wide") are filtered out. `field_location.id` is a list — an event spanning branches is attributed to every configured branch it names. **One source per branch on purpose**: a single all-branch query (no location filter) took ~3 minutes for ~360 events, so a timeout would cost every branch at once. Branches run one after another, so each after the first sleeps `pause_seconds` (default 5) first, and the entry's `timeout` is honored (it was once dropped, leaving the 30 s default on entries that asked for 90). A branch name that doesn't match the live list returns nothing with a `ccls_branch_not_found` log, not an error.
- **Library calendars** — one source type per platform the libraries use; each entry's `default_categories` carries the town slug plus `library`.
  - **LibCal** (`libcal_sources`, `sources/libcal.py`) — the page's own `GET /ajax/calendar/list?c=-1&date=0000-00-00`: every calendar at once, no `cid` to dig out, paged 50 at a time. Recurring events repeat under one `id`, so the event id is `<id>:<start>`. It still lists multi-day events that began before today; the source drops the ones already over.
  - **BiblioCommons** (`bibliocommons_sources`, `sources/bibliocommons.py`) — `gateway.bibliocommons.com/v2/libraries/<slug>/events`, public JSON; everything is under `entities`, merged across pages. One entry covers the whole Burlington County Library System; `branches` narrows it.
  - **Modern Events Calendar** (`mec_sources`, `sources/mec.py`) — no iCal export and no REST route on collingswoodlib.org, so it POSTs the month navigator's `mec_monthly_view_load_month` to admin-ajax. **The JSON-LD `startDate` is date-only; the time comes from the `<article>`'s "5:00 pm - 6:00 pm".** The grid pads with neighbouring months' days, so events dedup by url+date.
  - **Drupal FullCalendar** (`drupal_fullcalendar_sources`, `sources/drupal_fullcalendar.py`) — pennsaukenlibrary.org embeds its event list in `drupalSettings` (back to 2020; only upcoming are kept). Dates only: times and descriptions live on each node page, which isn't fetched.
  - **iCal feeds** (`ical_sources`) for LibraryCalendar (`<town>.librarycalendar.com/events/feed/ical`) and All-in-One Event Calendar (`/?plugin=all-in-one-event-calendar&controller=ai1ec_exporter_controller&action=export_events`). Haddonfield's feed has `LOCATION:US` on some events, hence the `venue_name`/`venue_address` override; berlinborolibrary.org's keeps events back to 2023, hence `upcoming_only`.
  - **The Events Calendar** (`tribe_sources`) covers the rest. runnemedepubliclibrary.org is behind Cloudflare: plain HTTP and the iCal URL 403, and the home-IP scraper is blocked too, but the droplet's browser got the REST JSON *some* of the time (an HTML "403 - Forbidden", not a challenge page, the rest), so `via_scraper` retries a few times. Later the site itself broke: Cloudflare answers even the Pi's browser with "520: Web server is returning an unknown error", every run fails it, and that alone keeps `schoolz-scan-warnings` firing for `local_events.refresh`. It stays listed so its stored events aren't pruned; drop it if the site doesn't come back. Libraries that set no venue on their events get `venue_name`/`venue_address` as a fallback.
  - Not collected, on purpose: barringtonlibrary.libcal.com, which is Barrington, *Rhode Island*'s library (281 County Rd; it was a source from 10-09 to 11-05, placed in Barrington, NJ by 0099's `location`, until its Providence Journal and Gardner Museum passes gave it away - check a library's own address before adding it), Stratford's Wix `/calendar` page (the events aren't in its HTML; the LibCal feed has them), Lindenwold/Magnolia/Somerdale/Berlin Township/Gibbsboro (no library calendar; the Camden County Library System branches cover what exists), Oaklyn and Woodlynne (Collingswood's library serves them). clementon-nj.com is the *township* calendar (My Calendar plugin, `/?feed=my-calendar-ics`) and holds only a handful of events.
- **Placewise mall sites** (`placewise_sources`, `sources/placewise.py`) — the events page server-renders into `__NEXT_DATA__`, plain httpx. The list mixes events with store promotions: a `date_range` with no end date is a standing sale and is skipped; store events are labelled "<store> at <mall>". A page without the events container raises, so a redesign is a WARNING rather than a quiet 0.
- **Event pages** (`event_page_sources`, `sources/event_pages.py`) — a town's hand-written festival pages with no feed (Collingswood's parade, tree lighting, Parade of Lights, holiday calendar; collingsweird.com/events). The theatre source's reader with an events prompt: a title must appear in the page text, what Haiku read is stored by page-text hash in `page_extractions`, so an unchanged page is never paid for twice, across deploys too (it was an in-process dict, and every deploy re-bought ~40 calls). **These pages outlive their event**, so two guards live in code, not the prompt: a weekday the page writes must match the date ("Join us Friday, October 10" on last year's page), and a date with no year written near its title is kept only within 120 days (300 when a matching weekday vouches for it) - the model claimed `year_written` for a page that had none. A weekly series is skipped unless its dates are written out; the same event on two pages (its own page and the holiday calendar) is kept once per start time. List each event's own page in `urls`; the arts index page is only links. `location` is appended to a venue the page names, so "Knight Park" geocodes. Use `exclude_title_patterns` for what a real feed already covers (Collingswood's farmers market is on the borough calendar).
  - **Indian Acres Tree Farm** (Medford; `indian_acres_tree_farm`, in `backend/seed/local_events.json`) — a GoDaddy Website Builder site. Its Calendar page's events are typed into the builder by hand (`manualEvents` in the page script, dates as free text like "11/20 - 1/3"), and the widget's `icalURL` is the builder's placeholder Google calendar, not the farm's: there is no feed. Only the light trail page is read, because it writes out every night with the year. The Calendar page would add the trail again as one 45-night range, nights it's closed included. The fall pages (pumpkin picking, mazes) aren't read either: they give a season ("Weekend Wagon Rides - September 19th thru October 25th"), which the reader skips as a weekly series. OpenStreetMap doesn't know the farm, so the trail is placed by `location` (Medford); the street address is the fallback for events the page gives no venue for. A page that writes out a whole season is why the reader's `max_tokens` is 16,000: a cut-off answer is never stored, so it would be bought again every run.
- **Ludus box offices** (`ludus_sources`, `sources/ludus.py`) — Collingswood's school theatre program (collstheater.ludus.com): plain HTML, one event per performance, no model call. Its Cloudflare refuses a plain request, so the source reads the scrapers' rendered copy, which works only while the site serves their browser the page. **It can challenge every visitor instead**, home addresses too, every page and robots.txt alike (the site has none: `/robots.txt` redirects to its 404 page). Then no scraper's browser gets the page, the Pi's included, with stealth or without: each gets "Just a moment...", and the challenge blows the render's memory budget. The source fails each run and keeps the events it has, and stays listed so it picks up again by itself. Getting past the challenge would mean defeating the bot check, so don't add stealth, the Pi or retries for it.
- **Patch.com** (`patch_sources`, `sources/patch.py`) — `patch.com/new-jersey/<region>/calendar` server-renders into `__NEXT_DATA__`, plain httpx. **One entry lists every region**, because regions repeat each other's events (and the same paid "promoted" placements) under one event id, and the source dedupes by id. Only a few regions have real newsrooms; many `-nj` slugs are thin, and placeholder slugs serve a different shape (`patchAmFreeEvent`: no link, no `displayDate`) that is skipped. Promoted placements come from anywhere in NJ, so `center`+`max_miles` filters on coordinates; many genuine local events carry a city but 0,0 coordinates, so no-coordinates is kept when a city/street is present and dropped when neither is (online webinars). A failed region is a `partial_failures` WARNING. Patch's robots.txt blocks several AI crawlers by name: keep to one daily-ish pass with a pause between regions, and check its terms before surfacing more than title/link/time.
- **Google Calendar IDs** — a bare id (no `@`) is auto-suffixed `@group.calendar.google.com` (billz stores some that way and the API 404s them). One dead calendar no longer sinks its source; it's a `local_event_source_partial` WARNING. The seeded job (migration 0049) uses billz's defaults minus phila.gov's city-government calendars (wedding schedules, tax board; one id 404s).
- **WXPN concert calendar** (`wxpn_concerts`, a `tribe_sources` entry on `xpn.org`) — Philadelphia-area independent-radio picks. Many shows carry only a date, no time, and the API says `all_day: false` with a `00:00:00` start, so `tribe.py` reads an exact-midnight start as all-day rather than a "12:00 AM" show (other tribe sources get the same rule). Most venues have no coordinates, so the zip-prefix fallback (190/191 plus 080/081) does the radius work; `max_miles: 30` from Cherry Hill reaches Ardmore, Glenside and Sellersville but not Allentown.
- **Do215 music** (`dostuff_sources`, `sources/dostuff.py`) — DoStuff Media's Philadelphia guide, plain httpx. The site is a SvelteKit app: each day page's data is read from the same path plus `/__data.json` (devalue-encoded; `_devalue` resolves it). A redesign dropped the schema.org microdata the first adapter read, and the rendered cards only say "Tomorrow | 9 pm". **The category is a URL path** (`/events/live-music-events-philadelphia/YYYY/MM/DD`): `?category=music` is silently ignored and returns the whole day (walks, comedy, museum shows), so the adapter doesn't offer a query filter and a wrong slug 404s loudly. Paged with `?page=N` (20 per page, `_meta.has_next`). A show that started the night before reappears on the next day's page, so events not starting on the requested day are skipped. Listings carry venue name but no street address (the venue's `location` is null), description, price or coordinates, so `locate.py` places them by venue name. 14 days × ~2 pages a run, one second apart; robots.txt allows `/events` but disallows map views. The same adapter covers any other DoStuff city (`do512`, ...) by changing `base_url` and `category_path`.
- **RunSignup races** (`runsignup_sources`, `sources/runsignup.py`) — the race search behind runsignup.com/races is a public JSON API (`/Rest/races`: zipcode + radius + date window, 250 a page), no key, plain httpx. One event per race, not per distance. RunSignup doubles as a sign-up form, so the search also returns virtual races, running-club memberships and whole sports seasons (a CYO cheer season is `event_type: "other"`): only in-person event types count. **The date comes from the in-person events' own `start_time`, never the race's `next_date`**, which is null on a series whose next leg is months out and points at the virtual week when a race has both. A series prints its last leg as every event's end time, so an end more than 48h after the start is dropped. `exclude_patterns` (regexes over title + street) exists for run-it-yourself race mills that list a real Camden trail as the address ("Course Map will be emailed") twice per title, and for organisers' test records. No coordinates; the radius is RunSignup's own, `states` narrows it (15 miles from Cherry Hill is about 40% Philadelphia).

## Town and county calendars

How to add one: `docs/ONBOARDING_CRAWL_GUIDE.md` → "Town and county calendars". These notes cover what's specific to each platform, plus the status of every town checked so far.

- **`skip_meetings`** (`local_events/filters.py`) works for any source type and is set on every municipal entry. It drops council, board and committee meetings, work sessions, caucuses and court sessions, but keeps town-hall, community and information meetings and office closures. Turning it on also deletes that source's upcoming stored rows that now match, so a filter added late cleans up after itself. `exclude_title_patterns` does the same with an entry's own regexes. Dropped counts go in the run summary's `excluded`.
- **CivicPlus**: use the iCal export, not `RSSFeed.aspx`. The RSS lists only the next ~2 weeks (on the same day: Cherry Hill 14 events vs 25, Burlington County 91 vs 125). **`catID` is one category per site**: 14 is Cherry Hill's "Main Events" but Haddon Heights' and Willingboro's federal holidays. Read the site's `/iCalendar.aspx`. CivicPlus also 429'd prod on 3 of 7 feeds fetched back to back, so `ical_sources` keeps CivicPlus entries apart from each other.
- **Revize JSON** (`parser: "revize"`) returns the town's whole history (Mount Laurel: 1,821 entries, 24 upcoming), hence `upcoming_only` on `json_sources`. It also carries the site's own setup entries ("Website review") and room bookings ("Pavilion – BOOKED"). The handler needs `webspace=` (the page source's `RZ.webspace`, e.g. `lumbertontownshipnj`) plus `relative_revize_url=//webgen1.revize.com&protocol=https:`; without them it answers 200 with "Incorrect data or missing data was passed to the calendar's data handler."
- **Revize's old `calendar_app`** (`revize_calendar_app_sources`, `sources/revize_calendar_app.py`): plain XML per calendar per month at `calendar_app/db/calendar_<id>_activemonthsdata_<YYYY-MM>.xml`. A repeating event lists every date in each month file it touches, so occurrences dedupe on (id, date). A date ending in "+" is a continuation day of a multi-day event, not a new occurrence. An empty month 404s, so the source checks `calendar_db_data.xml` first: otherwise a site that left the app would read as "no events" forever. That file's `published` date says nothing about the events (Collingswood's is 2022, and it has 50+ upcoming). **`news_feed: true` also reads the site's news list** (`newslist.php`): every post the town ever made on one ~2 MB page from a slow server (it 504'd for ~20 minutes once), so only the last 45 days are read, the same way as Apptegy live-feed posts below.
- **Apptegy town sites** (`thrillshare_sources`): the same API as the school calendars (`services/apptegy.py`), with the town's own org id. Coordinates come as strings, "" when there's no pin. **`live_feed: true` also reads the site's Live Feed posts** (`cms/live_feeds`): Oaklyn announces its picnic, movie nights and Green Day there, never on the calendar, among gas-main work schedules, spraying notices and agendas. Each post goes through the event-page reader once ever, prefixed with its posting date so "Sunday, October 18th" lands in the right year. A post that moves or cancels an event takes back the date an earlier post gave (`moved_from`/`cancelled`). The model used a title-only image post's *posting* date as its event date, so an event dated the day it was posted is dropped unless the post's own text has date words. **Flyer images are read** (`sources/flyers.py`, shared by both feeds): Haiku copies each image's words (up to three per post), then the post text plus the flyer text goes through the reader, so a flyer's title still has to appear in that text. Agendas, maps, photos and logos come back NONE. A transcription is stored by a hash of the image bytes, so each image costs one call ever; a school feed full of classroom photos would cost a call per photo, which is why it isn't switched on there.
- **Blocked from Fly's egress IP since 2026-10-15 16:00 UTC**: `haddonfield.librarycalendar.com`, `mountlaurel.librarycalendar.com` and `xpn.org` started 403ing prod at the same run. The same code, httpx version and image get 200s from elsewhere, so it's the IP (all three hosts answer as nginx), not that day's httpx 0.28 bump. They use `via_scraper` now. If another plain-HTTP source starts 403ing on prod alone, try that first.
- **Woolwich's SiteGround turns away the scheduler machine** (`woolwichtwp.org`, Tribe): from its first run it answered the refresh with a page that isn't the JSON (`JSONDecodeError` at char 0), while a test-fetch on the API machine, a home address and the droplet all got the JSON. No Chromium loads a SiteGround site (`ERR_HTTP2_PROTOCOL_ERROR` from every scraper, even at home), so `via_scraper: true` can't help; it is `"via_scraper": "request"`, the droplet first, with no Pi. A scraper whose answer isn't a JSON object hands over to the next.

- **EvoGov** (Lawrence Township, East Windsor): public per-calendar iCal at `/meetings/icalendar/calendar/<id>/`, listed on `/meetings/icalendar`; `ical_sources` with `upcoming_only`, since it keeps past events. **DPCalendar's raw feed returns 20 events by default**: Ewing's stopped at two weeks out until `&limit=500`. **CivicPlus 404s a comma-separated `catID`**, so each category is its own entry.
- **RSS through a scraper** (`rss_sources` with `via_scraper`, optionally `prefer_residential`): the scrapers' raw fetch returns the page Chromium shows for a feed it displays rather than downloads, the XML escaped inside a `<pre>`, which `rss.py` unwraps. A description whose HTML was escaped twice (Fieldsboro's "&lt;div dir=...&gt;") is decoded to text there too, since the normalizer strips tags but not entities.
- **CivicPlus on Drupal**, both generations, sits behind a Cloudflare challenge that the datacenter scrapers don't get past (the droplet 502s, Fly's scraper blows its 700 MB budget), so its entries are `ical_sources` with `via_scraper` and `prefer_residential`: one Pi load each a run. **HCMS** (Drupal 11: Magnolia, Eastampton, Chesterfield; Fieldsboro runs it too): `/calendar/ical/calendar.ics` is the whole calendar back to 2017, hence `upcoming_only`, while `/calendar/rss` lists only the next 10 entries (enough for Fieldsboro; Magnolia's ten were all trash days). Every date of a repeating entry carries the series' UID, so a series with two upcoming dates is stored once; so far only pickups, tax dates and meetings repeat. Titles and descriptions come HTML-escaped (Eastampton's "Trunk-or-Treat &amp; Bonfire"), and each description opens with its field's label on a line of its own ("Body", "Description"); `ical.py` decodes the one and drops the other. **Drupal 7** (Gloucester City, Westampton): `/calendar/ical/export.ics`, the `webcal://` link on `/calendar/month`, one VEVENT per date. Its LOCATION is the rendered address block, country and "See map: Google Maps" included, which `ical.py` trims.
- **Google Calendar town calendars** go in `ical_sources` on the calendar's public `basic.ics` with `upcoming_only`, no key. The six `gcal_sources` entries (phila.gov, Barrington, Stratford, Cinnaminson, Maple Shade, Medford) all use phila.gov's own API key, taken from its events page and sent with phila.gov's referer, so no new entry should. The iCal reader doesn't expand RRULEs: a weekly series shows only its first date.

## Categories

`normalizer.py` keyword categories: every alternation must be grouped, `\b(?:a|b)\b`. The billz-ported `\bsport|game|race|run\b` bound `\b` to only the first and last word, so "art" in "start"/"party" tagged most of the feed `arts`. **Classes & Lessons** (`classes-&-lessons`) trusts the title, but a description only with sign-up wording: bios say "began piano lessons at 3" and blurbs "over the course of". A same-source refresh recomputes categories; a cross-source merge only unions them. **Volunteer & Give Back** (`volunteer-&-give-back`: volunteering, days of service, food/toy/coat/blood drives) is matched on **titles only**: library and town blurbs say a club is "run by volunteers" (Tutor Time, chess afternoons), and "Volunteer Fire Company" is an organizer, not a call for help.

## Pipeline notes

Community events — **public, no auth dependency at all** (no per-viewer personalization). `backend/local_events/` is a **port of billz's `events/` pipeline** and `local_events.refresh` takes billz's `events.refresh` params verbatim (Scans → **Import from billz**).

- Admin UI is billz's: JSON params editor + **Test fetch** (`POST /scheduled-jobs/test-fetch`, a dry run with per-source status). Test before saving.
- Rendering goes to the shared Playwright droplet first, schoolz's own scraper second; the residential Pi is opt-in per call.
- **A direct request names schoolz, never a browser**: `schoolz-local-events/1.0` (Revize and evvnt send `Mozilla/5.0 (compatible; schoolz-local-events/1.0)`, the bot form of the same). Software that isn't a browser doesn't say it is one, and `tests/test_local_events.py` fails on a browser's User-Agent anywhere in `local_events/`. Twelve source types came from billz with Chrome's and switched without losing a source: the two sites that refuse the honest name (Ludus, Yodel) refused Chrome's from prod too and were already read through the scrapers, whose browser is a real one. Judge a refusal from prod (a test-fetch), not from the droplet alone: Collingswood's flyer images (`cms6.revize.com`, behind Cloudflare) block the droplet's address whatever the User-Agent, while prod's API machine gets them.
- **Reviewer-published events** — an admin can publish a draft from a community submission (`/admin/submissions`) as a local event by choosing "Local events" as where it goes; no school needed. They are stored with `source="community"`, which no job lists, so `prune.COMMUNITY_SOURCE` is exempt from the orphan delete (`tests/test_placewise_source.py` pins it). Unpublishing deletes the row.
- **Localz provider dates** — "Post a date" on a Localz listing (`routers/provider_portal.py`) stores a `source="localz"` event with `resource_service_id`, deleted with the listing. Also exempt from the orphan delete (`prune.LOCALZ_SOURCE`). A feed listing the same event can add categories to a `community` or `localz` row but never rewrites it (`deduper.merge_into`).
- **Deleting a job, or removing a source from its params, deletes that source's events** (`local_events/prune.py`), by source name across all remaining jobs. Disabling keeps them. **`prune.SOURCE_KEYS` must list every `*_sources` key** or every job edit deletes that source's events as orphaned (`tests/test_placewise_source.py` checks this).
- A failed source makes the run `WARNING` (billz only marks it `-1`).
- **Local compose scraper binds `0.0.0.0`**: the image binds `::` for Fly's IPv6-only 6PN, and asyncio makes that socket IPv6-only locally.
- **`uvicorn --reload` watches `backend/` incl. `tests/`**, so editing any file kills a run-now job in the API process. Run long jobs from `schoolz-scheduler-local` (`SCHEDULER=1`).
